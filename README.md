# 小程序从需求到验收：交付清单

这是一份面向产品、研发与运营协作的小程序交付清单。它不替代具体业务的需求文档，而是帮助团队在上线前检查高风险环节是否已经被明确、实现并验证。

## 1. 把需求写成可验证的业务动作

每项需求至少包含操作者、触发条件、处理规则、成功结果和失败反馈。以商品下单为例，除了“提交订单”，还要写清库存不足、重复提交、价格变化、支付超时、取消和退款时的数据状态。

## 2. 服务端承担关键业务规则

- 价格、优惠、运费和库存以服务端重新计算的结果为准。
- 订单创建、库存扣减和库存回补应具有一致性，避免超卖或重复下单。
- 支付回调必须幂等，同一支付通知重复到达不能重复记账。
- 用户、商家和管理员的数据权限要在接口层验证，不能只依赖前端隐藏按钮。

## 3. 上线前的异常路径检查

| 场景 | 预期结果 |
| --- | --- |
| 连续点击提交 | 同一业务请求只产生一次有效记录 |
| 库存不足 | 阻止创建订单并返回可理解的提示 |
| 登录失效 | 清除失效会话并引导重新登录 |
| 网络超时 | 给出重试入口，避免用户重复发起不可控请求 |
| 无权限访问 | 服务端返回拒绝响应，且不泄露其他用户数据 |

## 4. 可追溯的交付证据

每次发布应保留版本号、数据库变更说明、接口变更、回滚步骤和关键流程测试记录。发生异常时，日志中应有请求标识、操作人、时间和变更前后的状态，便于定位和恢复。

## 5. 公开项目的评估方法

评估一个可复用项目时，不只看界面数量。应实际走通登录、创建、查询、修改、取消和后台处理等路径，并检查数据是否真实落库、权限是否隔离、异常是否能恢复。
